# 07 · 线上与仓库版本核对清单

> **这份文档解决一个问题**：以后想知道 GitHub 仓库和线上服务器是否一致，
> 不用再从头到尾翻一遍项目 —— 跑一条命令，对着「当前基线」表逐行比对即可。
> 一致就完事；只有某一行对不上时，才需要去查那一项。

---

## 一、为什么用「指纹」而不是 commit hash

线上 `/opt/portfolio` **没有 `.git` 目录**，无法直接 `git log` 比对提交号。
所以这里把**构建产物的哈希**当作版本号：

- 前端重新构建 → `index-xxxx.js` 的哈希必变
- 后端重新打包 → `app.jar` 的 sha256 必变
- Nginx 配置改动 → 配置文件 md5 必变

指纹变了就一定重新部署过；没变就一定还是旧的。**这比"我记得部署过"可靠。**

## 四、某一行对不上时，去哪查

| 不一致的行 | 含义 | 该去的地方 |
|---|---|---|
| 前端构建 / 前端样式 / 前端时间 | 前端代码改了但没重新部署 | `web/` → `npm run build` → 传 `dist` 到 `/opt/portfolio/web` |
| 后端构建 / 后端时间 | 后端代码改了但没重新打包 | `server/` → `mvn package` → 换 `app.jar` 并重启 |
| Nginx 配置 | 配置改了没同步（或线上手工改过） | 比对 `deploy/nginx.conf` 与 `/etc/nginx/conf.d/portfolio.conf` |
| PATCH 放行 = 未放行 | **后台改状态会 405** | 见附录 A |
| 服务不是 active | 服务挂了 | `systemctl status <服务>` / `journalctl -u portfolio -n 50` |
| 运行时版本 | 系统组件被升级过 | 一般无需处理，确认升级是有意的即可 |

### ⚠️ 这两行变化是正常的，不用管

- **内容版本**：后台每次保存内容就 +1，是数据不是代码
- **素材数量**：后台上传/删除素材就变，是数据不是代码

**只有「构建指纹」和「服务状态」才代表代码是否同步。**
