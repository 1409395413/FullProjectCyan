## 后台

### 1 · 历史快照只保留最近 10 个

**现状实测**：`content_revision` 表 **22 条**，合计 **0.2 MB**。后台每点一次「保存」就新增一条**整份 content JSON** 的拷贝；回滚时还会再存一份当前状态作为备份。

现在量小，但 payload 会随模块/素材线性变大，长期不收敛。

**细化规则**

| # | 规则 |
|---|---|
| 1.1 | 保存成功后**立即裁剪**：只留 `created_at` 最新的 10 条，其余物理删除（不是打标记） |
| 1.2 | 双重上限：条数 ≤ **10** 且 总量 ≤ **50 MB**，任一超限就删最旧的（防以后单条 payload 变大） |
| 1.3 | **相同内容不重复存**：新快照与最新一条 payload 完全一致时跳过写入（连点保存不产生冗余） |
| 1.4 | 回滚产生的「当前状态备份」同样计入 10 条配额，一起裁剪 |
| 1.5 | 后台快照列表标注「共 N 条 · 自动保留最近 10 条」，让你知道有裁剪这回事 |
| 1.6 | 裁剪在事务内执行，失败不影响本次保存结果 |

**❓ 待拍板**

- **1-A**：是否要「锁定快照」（给某条打 ☆，裁剪时跳过）？
  - 建议 **不加**。回滚只能回到 10 次保存内，一般够用；加了多一个概念要维护。
  - 若你担心误操作删过头，我加一个 ☆ 收藏，收藏的不参与裁剪。

**验收**：连续点保存 15 次 → 表里只剩 10 条且是最近的 10 条；回滚功能仍正常；重复保存同一内容不新增记录。

### 2 · 监控图表化（含地图板块、图表板块）

**现状实测**：监控页现在是「5 个数字卡 + CSS 柱状图 + 播放榜列表 + 最近访问列表」。`visit_session` 表 **85 条**。

#### ⚠️ 先说一个硬阻塞：地图现在做不出数据

`visit_session` 表结构里**只有 `ip_hash`，没有任何地域字段**——IP 在入库时就被哈希丢弃了。所以：

- 要地图，**必须先改采集**：新增 `region`（省）+ `country` 字段，在会话入库那一刻用**原始 IP** 查一次地域，只把「省名」存下来，IP 仍然只存 hash（保持现有「不采集身份信息」的声明）。
- **历史 85 条无法回溯出省份**，旧数据省份只能显示「未知」。

#### ⚠️ 再说一个合规约束：中国地图不能随手画

中国地图轮廓必须使用**有审图号的合规底图**（自然资源部标准地图服务）。自己用 SVG 描一遍省界属于不合规地图，有实际风险。

#### 细化规则 — 采集改造（做地域板块的前提）

| # | 规则 |
|---|---|
| 2.1 | `visit_session` 新增 `region`（省/直辖市，如「广东」）、`country`（默认「中国」，海外存国家名）、可选 `city` |
| 2.2 | 入库时用原始 IP 查一次地域，只存省名字符串；IP 依旧只落 hash |
| 2.3 | 地域库：离线库 ip2region（~10MB 本地文件，零网络依赖、零费用、精度到省市） |
| 2.4 | 查不到时写「未知」，不阻塞会话记录（地域只是附加信息，不能拖垮主流程） |
| 2.5 | 只对改造后的新会话生效；旧数据省份显示「未知」 |

#### 细化规则 — 板块划分

| 板块 | 内容 | 说明 |
|---|---|---|
| ① 概览卡 | 今日访客 / 平均停留 / 播放 / 播放率 / 待处理需求 | 每张卡加「较昨日 ↑↓ x%」环比箭头 |
| ② 每日趋势 | SVG 折线 + 面积图，7/14/30 天切换 | hover 出 tooltip：当天访问数 · 播放数 |

| ④ 地域分布 | ❓ 地图 或 省份榜（见 2-A） | 需先看 2.1~2.5 |
| ⑤ 设备与来源 | UA 解析「手机/平板/桌面」占比环图 + 浏览器 TOP5 + 来源 referrer TOP5 | UA 已有数据，不用改采集 |
| ⑥ 作品播放榜 | 横向条形图 + 占比 | 现有列表升级 |
| ⑦ 转化漏斗 | 访问 → 播放作品 → 提交需求，三级漏斗 | 新增 |
| ⑧ 最近访问明细 | 保留现有，追加「地域 / 设备」两列 | 现有升级 |

每个板块独立空态文案（现在数据少，空态比图表更常见）。

#### 细化规则 — 技术选型

手写 SVG 图表，**不引图表库**。理由：现有柱状图就是手写的，风格一致；echarts 要 ~1MB，为一个后台页面不值；uPlot 之类的也要 +45KB。手写约 +15KB 且完全可控。

### 4 · 上传增加「从素材库添加」

**先纠正一个认知**：后端**已经有 sha256 秒传去重**（`media_asset.checksum` 有索引，同内容文件重复上传会直接复用既有路径，不占新空间）。所以「重复添加」**不会**真的翻倍占存储。

但它仍有三个真问题，这才是需求 4 的价值：

1. 41 MB 的文件**重传一遍要等很久**（公网上传远慢于下载）；
2. 你不知道自己**已经传过**，于是又传了一次；
3. 同一内容在不同模块是**两条独立的条目记录**，改标题、改画框要改两遍。

**细化规则**

| # | 规则 |
|---|---|
| 4.1 | 素材编辑器「上传」按钮旁增加「**从素材库选取**」 |
| 4.2 | 弹出素材库面板：**复用需求 3 的筛选/搜索/排序**，单选插入 |
| 4.3 | 插入即把该素材的 url / 类型 / 宽高 / 时长填进当前条目 —— **不产生新文件、不产生新记录** |
| 4.4 | 视频自动带出首帧 poster 与时长标记（依赖 P0-1 的 poster 生成） |
| 4.5 | 面板里给已在本模块用过的素材打「已在此模块」标，避免同模块重复挂 |
| 4.6 | **多选批量插入**：一次勾多条，按勾选顺序插入（叠牌画廊很需要） |
| 4.7 | 上传完成后若命中秒传，UI 提示「已存在，直接复用」 |

**❓ 待拍板**

- **4-A**：是否要在**上传前**就在前端算 sha256 做秒传预判？建议 **不做**——几十 MB 的文件在浏览器里算哈希会卡住页面，收益（省一次上传等待）不如代价。后端秒传已经兜底了。

**验收**：从素材库选一条插入 → `media_asset` 数量不变、磁盘占用不变、前台正常显示。

## 前台：交互流畅、不卡顿

### 先量化 —— 卡顿 90% 来自视频，不是前端代码

| 项 | 实测值 | 判定 |
|---|---|---|
| 首页 TTFB | **0.058s** | ✅ 很快 |
| `/api/content` | 0.18s / 10KB（带缓存） | ✅ 很快 |
| 主 JS（gzip） | 13 KB + vue 38 KB | ✅ 很小 |
| 主 CSS（gzip） | 9.8 KB | ✅ 很小 |
| 静态资源缓存 | `expires 30d` | ✅ 已配 |
| gzip | 已开，level 5 | ✅ 已配 |
| 首页 `Cache-Control` | **no-cache**（每次必回源） | ⚠️ 可优化 |
| HTTP 协议 | **1.1**（未开 h2） | ⚠️ h2 需 HTTPS，备案未下暂不可 |
| **视频总量** | **5 个 / 194.6 MB** | 🔴 **真瓶颈** |
| 竖屏视频码率 | **14 Mbps**（1080×1920@60fps） | 🔴 远超实际吞吐 |
| 公网实测吞吐 | **0.7 ~ 2.2 MB/s** | 🔴 14Mbps ≈ 1.75MB/s，卡在临界 |
| 图片原始尺寸 | 3840×2160、4096×1024 | ⚠️ 远大于展示需要 |
| 服务器内存 | 2G，Java 占 500M，剩 92M + swap | ⚠️ 转码必须限线程 |

**结论**：JS/CSS 加起来才 60KB，不是问题。卡的是你那 5 个视频——尤其 14Mbps 那两个竖屏，实测带宽刚刚好喂不饱它。

### 细化方案（按性价比排序）

  - 否 → 我先只做 P0-1/P0-2/P0-4（不动原文件），转码等你挑时间。
- **6-B**：转码目标档位要保守（3 Mbps）还是激进（1.5 Mbps，体积小一半但暗部可能出现色带）？建议 **保守 3 Mbps**——你的作品是影像类，画质是门面。

**验收**：转码后单个视频 ≤ 原体积 1/4；4G 模拟下首页从打开到首屏画面出现 < 2s；滚动无明显掉帧；任意时刻正在播放的视频数恒为 1（首屏除外）。
